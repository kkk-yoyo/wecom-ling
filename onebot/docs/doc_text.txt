前言
本手册面向需要把微灵（WeComSever）接入 OneBot v11 机器人框架的开发者与运维人员，说明微灵 1.11.0 改造版如何以 OneBot v11 反向 WebSocket 客户端 的身份接入 AstrBot、NapCat、LLOneBot 等支持 OneBot v11 的机器人实现，并给出配置、协议、事件、动作、排障的完整说明。
文档目的
微灵 1.11.0 改造版在进程内替换了原有的自研 WebSocket 通道实现，把「微灵事件 → OneBot v11 事件」和「OneBot 动作 → 微灵指令」两件事在微灵内部完成翻译。因此对接方不再需要自行实现微灵私有的 hello / ping / command 帧，也不必处理 11170/11171 的二进制文件流，只需部署一个支持 OneBot v11 反向 WS 的机器人框架，在微灵界面里填写地址与 Token 即可完成对接。
读者对象
•  部署运维人员：按第 2 章完成 AstrBot 与微灵的两侧配置，按第 12 章排查问题。
•  机器人开发者：阅读第 4～7 章，了解连接握手、事件帧、消息能力矩阵、动作请求与错误码约定。
•  二次开发人员：阅读第 6 章消息能力矩阵、第 8 章媒体说明、第 10 章兼容性说明与附录中的事件号/指令号速查表。
与官方文档的关系
微灵官方《微灵对接文档》（1.11.0）描述的是 HTTP 接口与自研 WebSocket 协议，这些内容在改造版中仍然有效：HTTP 8060 接口、HTTP 事件回调、微灵指令号均未改变。本手册只描述改造后的 OneBot v11 通道；当两者表述冲突时，以本手册及实际实现（D:\wecom-ling\onebot\src\WxSocketClient.cs）为准。
提示　本手册的行为描述依据 1.11.0 改造版的实现编写。微灵后续版本可能扩展事件与动作，升级后请以对应版本的变更说明为准。

1　改造概述
1.1　改造背景
微灵原方案通过一套自研 WebSocket 协议把微信事件推送给对接方：微灵作为客户端连接对接方自建的 WS 服务端（企微通道路径为 /wx/ws，个微通道为 /personal-wx/ws，Token 以 ?token= 形式附加在 URL 上）。对接方需要自行实现握手（hello）、心跳应答（ping/pong）、事件帧（event）、指令帧（command）与二进制文件流，协议细节多、排障成本高，且无法直接复用已有的 OneBot 生态。
改造版把微灵进程内的 WebSocket 通道替换为 OneBot v11 反向 WebSocket 客户端：微灵仍然主动向外建立 WebSocket 连接，但说的是 OneBot v11 标准协议；连接目标从“对接方自建服务端”变成“现成的 OneBot v11 实现”（AstrBot 的 aiocqhttp、NapCat、LLOneBot 等）。微灵内部继续使用原有的指令体系与事件采集链路，协议翻译在进程内完成，不改变微灵的登录、收发消息和部署形态。
1.2　改造后架构
改造只替换微灵的“WS 出口”，整体链路如下：

      ▼
┌────────────────────────────── 微灵进程（1.11.0 改造版）──────────────────────────────┐

•  连接方向不变：微灵仍是 WebSocket 客户端，主动连接 OneBot 实现提供的反向 WS 服务端。
•  协议改变：握手、事件、动作全部使用 OneBot v11 的 JSON 帧；微灵私有帧不再出现在 OneBot 通道上。
•  翻译在进程内：事件侧把微灵事件转成 OneBot 事件并保留原始事件（ling 字段）；动作侧把 OneBot 动作转成微灵指令，通过微灵原有命令通道执行。
•  零额外进程：不需要再部署一个 WS 网关；只需在微灵界面填写 OneBot 实现的地址与 Token。

1.4　设计原则与兼容性
•  最小侵入：不改变微灵登录、收消息、发消息与群管理的原生链路，只替换 WS 出口；部署形态仍是单个微灵进程。
•  原样保留：所有 OneBot 事件都附带 ling 字段，内含完整微灵原始事件（仅剔除体积最大的 data.payload_base64），便于高级用户读取 OneBot 未覆盖的字段。
•  显式失败：首版未实现的动作返回明确的 failed 与错误说明（retcode 1404/500），不会静默丢帧，便于快速定位。
•  兼容旧能力：微灵原有 HTTP 8060 API、HTTP 事件回调、微灵 UI 与 config.ini 均保留，改造只影响 WebSocket 通道。
•  能力边界清晰：出站支持文本、@ 与图片/视频/文件/动图（语音除外），入站媒体取回依赖事件自带 CDN 直链，这些限制集中记录在第 8 章与第 12 章。
限制　改造版不提供语音发送，也不支持撤回、群管理、请求处理等动作；详见 7.6、7.7 节与 12.3 节。若业务强依赖这些能力，请评估后再切换。

2　快速开始
本章以 AstrBot 4.29.0 + 微灵 1.11.0 改造版（企微通道） 为例，完成从零到“收发一条消息”的最小闭环。全流程约 10 分钟。读者只需照做并在最后完成验证，即可确认 OneBot v11 通道工作正常。

# AstrBot aiocqhttp（OneBot v11）平台配置示意

ws_reverse_port: 6200

2.3　微灵侧配置
步骤 1　启动微灵 1.11.0 改造版，完成企业微信登录，等待界面显示账号在线。
步骤 2　进入微灵的连接/通信设置，把「通信方式」选择为 WebSocket。
步骤 3　「WebSocket 地址」填写 ws://127.0.0.1:6200/ws（AstrBot 与微灵同机）。跨机部署时把 127.0.0.1 换成 AstrBot 所在主机 IP。
步骤 4　「Token」填写 114514，与 AstrBot 的 ws_reverse_token 完全一致。
步骤 5　保存配置并启用。微灵将作为客户端连接 AstrBot，连接状态显示为“已连接”（或同义状态）。
个人微信通道的填写方式相同，但需要在微灵中选择「个人微信 + WebSocket」通道，并填入该通道对应的 OneBot 实现地址；个微通道没有默认地址，地址为空时不会连接。个微通道的能力与限制见第 9 章。

2.4　启动与验证
按以下顺序启动，避免微灵先启动、找不到监听端而反复重连：
步骤 1　启动 AstrBot，确认 aiocqhttp 适配器已启用、6200 端口处于监听状态。
步骤 2　启动微灵并登录企业微信；登录成功后微灵才会解析出 self_id 并发起连接（见 4.6 节）。
步骤 3　在微灵中启用 WebSocket 通信方式，地址与 Token 按表 2-3 填写。
步骤 4　观察两侧状态：AstrBot 日志应显示 aiocqhttp 客户端接入/连接成功；微灵界面应显示已连接，微灵程序目录下 onebot_v11.log 中可见连接成功记录。
步骤 5　发消息验证：用企业微信给机器人账号发一条私聊消息，AstrBot 应收到 message 事件；再让 AstrBot 向该会话回复一条文本，企业微信侧应能收到。

2.5　首次接入常见问题
•  微灵一直不连接：多为微灵未登录成功、或 8060 端口不可用导致取不到 self_id。先确认微灵账号在线，再查看 onebot_v11.log 中是否有等待 self_id 的记录。
•  连接被拒绝（401/403）：两侧 Token 不一致或微灵 Token 为空。Token 走请求头，URL 里不需要也不支持 ?token=。
•  连接 404 或握手失败：地址缺少 /ws 路径，或 AstrBot 的反向 WS 路径被修改。按 3.3 节规则补全路径。
•  连上但收不到事件：检查消息是否为账号自己发出（会被过滤）、事件类型是否属于未映射类型，或 AstrBot 适配器未启用；详见 5.7 节与 12.2 节。
•  AstrBot 回复失败：文本/@/图片/视频/文件/动图已支持发送（图片等媒体先落盘到 onebot_media_tmp）；语音（record）与 json/xml/forward 等段不支持，会返回 failed。若 msg 为“微灵未返回结果（超时或未登录）”，说明微灵侧登录或指令通道异常（见 8.2 节）。

3　部署与配置
本章说明运行环境要求、改造版的部署形态、地址与 Token 规则、微灵可配置项，以及对接 AstrBot 之外其他 OneBot v11 实现时的要求。核心结论是：微灵只负责主动连接，配置只有地址与 Token 两项，其余参数均由 OneBot 实现侧决定。
3.1　运行环境要求（重要）
部署前请先确认运行目录：微灵必须放在不被本机安全软件或终端管控策略限制的普通目录中运行。现场已定位：若程序目录被列入受限路径，会出现一组与 OneBot 改造补丁无关的故障——企业微信注入失败、HTTP 8060 不监听、无法写入 C:\Users 目录等；同一份 exe 复制到普通目录后立即恢复正常，说明问题在运行环境而不在程序或补丁本身。
结论先行　推荐目录：D:\微灵OneBotV11\（本机已验证）。不要放在 D:\wecom-ling\、C:\Users\...\Downloads、VDI 同步盘等可能被安全策略/沙箱管控的路径下运行。移动时把整个程序目录一起复制，不要只移动 exe。

换到可信目录后的实测现象，可作为验证基线：
•  HTTP 8060 秒开，日志出现「服务已启动，监听地址: http://0.0.0.0:8060/」。
•  企业微信注入成功：proxy /api/status 返回 hooks_installed=true、tcp.connected=true，客户端上线；日志出现「已接入 5.0.13.6005 pid=… client=1 http=19065 tcp=19167」。
•  父进程信任会传染：注入器由受限目录中的进程启动时同样失败，改由可信目录中的进程启动即成功。
提示　该限制来自终端安全/沙箱策略（本机为传云 Vault + CloudEDR / HIoTSecAgent），与 OneBot 改造补丁无关。换到普通目录即可，不需要改配置、重装或调整补丁；若换目录后仍异常，再按第 12 章排查。
3.2　部署形态
•  单实例单连接：一个微灵进程的企微通道建立一条 OneBot v11 WebSocket 连接；个微通道（实验性）单独建立一条连接。两条通道互不影响。
•  OneBot 实现在对端：AstrBot / NapCat / LLOneBot 以“反向 WS 服务端”身份监听端口，微灵以客户端身份连接；不需要在微灵侧开放任何入站端口。
•  无需额外进程：协议翻译在微灵进程内完成；部署组件与未改造版本完全一致，仅多一个 OneBotShim.dll。
•  多账号/多实例：每个微灵实例各自填写自己的 OneBot 地址；OneBot 实现侧可通过 X-Self-ID 区分不同账号，或为每个账号配置独立适配器。

3.3　连接地址规则
微灵在连接前会对界面中填写的地址做一次规范化，规则如下（按顺序执行）：
步骤 1　地址为 空 时：企业微信通道自动使用默认地址 ws://127.0.0.1:6200/ws；个人微信通道不连接。
步骤 2　去掉首尾空白后，按前缀替换协议：http:// → ws://，https:// → wss://；没有任何协议前缀时自动补 ws://。
步骤 3　解析 URL；解析失败则放弃本次连接并按退避策略重试。
步骤 4　路径为空（或仅为 /）时补 /ws；已有路径保持不变。
步骤 5　保留查询参数（?a=b）；连接时不额外附加参数。
表 3-4　地址规范化规则

注意　Token 不要写进地址（如 ?token=xxx）。改造版通过 Authorization: Bearer 请求头传递 Token；把 Token 放在 URL 中会出现在日志与代理记录里，且可能被服务端忽略。
3.4　Token 与鉴权
•  Token 不为空时，微灵在 WebSocket 握手请求中携带请求头 Authorization: Bearer <token>。
•  Token 为空时，不发送 Authorization 头；若 OneBot 实现配置了 Token，握手会返回 401/403。
•  鉴权失败不会停止重试：微灵按 1s～30s 退避持续重连，因此配置错误时会周期性出现握手失败日志。
•  Token 只用于握手鉴权，连接建立后不再校验；更换 Token 后需要断开重连（重启微灵或切换通信方式）才生效。
•  若某个 OneBot 实现仅支持 ?token= 查询参数、不支持请求头，可在微灵地址中显式带上查询参数（查询参数会被保留）作为兼容手段，但不推荐用于生产。

4　连接与协议
本章描述微灵作为 OneBot v11 反向 WS 客户端时的完整链路：如何取到 self_id、握手携带哪些信息、连接后交换哪些帧、失败时如何重连。所有行为均为改造版实际实现，可直接用于自研 OneBot 实现或抓包排障。
4.1　连接流程
微灵的连接是一个后台网络循环，与登录状态解耦：账号未登录时循环仍在运行，但不会发起连接。完整流程如下：
步骤 1　解析 self_id：内存中已有则直接使用；否则每 15s 通过微灵 HTTP API 查询一次（企微通道，指令 11035），直到取得 user_id。个微通道跳过此查询，依赖事件中的 robot_id 或登录事件。
步骤 2　生成连接地址：按 3.3 节规则规范化；若地址无效或为空（个微），本次不连接，等待下一轮。
步骤 3　发起 WebSocket 握手，携带 X-Self-ID、X-Client-Role: Universal 与 Authorization 头，最长等待 15s。
步骤 4　握手成功后立即发送 meta_event.lifecycle.connect，并启动接收循环与发送循环。
步骤 5　运行期：每 30s 发送心跳；把微灵事件翻译为 OneBot 事件后发送；执行对端下发的动作。
步骤 6　连接断开（对端关闭、网络错误或发送超时）后清理状态，按 1s 起、上限 30s 的指数退避重连。
排障入口　连接状态变化会通知微灵界面（已连接/未连接）。排查时优先看微灵程序目录下的 onebot_v11.log，其中记录了地址、self_id、连接结果与失败原因。
4.2　握手请求头
微灵在 WebSocket 握手（HTTP Upgrade）请求中固定携带以下头：
表 4-1　握手请求头

•  连接超时为 15s；ClientWebSocket.KeepAliveInterval 设为 20s，用于保持底层 TCP 连接活跃。
•  Token 只出现在请求头中，不会出现在 URL、日志正文或事件里。
•  握手被拒绝（401/403/404 等）时不会无限快速重试，而是进入指数退避。
4.3　元事件：连接与心跳
连接建立后，微灵主动发送两类 meta_event。对端可据此确认连接可用，并刷新账号信息。
4.3.1　连接事件
握手成功后立即发送一次，sub_type 固定为 connect：
代码 4-1　lifecycle.connect
{
  "time": 1731452400,
  "self_id": 168800001,

  "meta_event_type": "lifecycle",

4.3.2　心跳事件
连接期间每 30s 发送一次；status 固定为在线且正常，interval 固定 30000（毫秒）：
代码 4-2　heartbeat
{
  "time": 1731452430,
  "self_id": 168800001,
  "post_type": "meta_event",
  "meta_event_type": "heartbeat",

}

所有事件都是单行 JSON 文本帧，顶层包含通用字段，再按 post_type 追加类型字段。以一条群消息为例：

  "font": 0,

•  message 为消息段数组，段类型与字段见第 5 章；raw_message 为文本与 @<QQ> 的拼接结果。

代码 4-4　动作请求

代码 4-5　动作成功响应

  "retcode": 0,
  "msg": "",
  "data": { "message_id": 88776602 },

•  params 缺失或为 null 时按空对象处理，由具体动作校验必填参数。

不再有静默看门狗　接收侧固定读超时已移除；发送线程的 120s 入站静默看门狗也已移除（源码常量已删除），不存在因空闲静默而周期性重连。AstrBot 等 OneBot 实现空闲时通常不发帧，连接有效性依赖 ClientWebSocket.KeepAliveInterval（20s）的保活探测与发送失败处理；链路中断会在下一次发送失败或 KeepAlive 探测失败时进入退避重连。

5　事件映射
微灵把企业微信的原始事件翻译为 OneBot v11 事件后推送给对端。本章逐类给出映射关系、字段来源与过滤规则。未列出的微灵事件一律不上报，仅在日志中记录一次。
5.1　通用规则
•  会话方向：优先解析微灵事件的 conversation_id。R:<room_id> 视为群聊，group_id 取 <room_id>；S:<peer>_<self> 视为私聊，user_id 取 <peer>。解析失败时按 conversation_type 判断：group 为群，其余（含 customer_service）为私聊，对端用户取 sender。
•  过滤自身消息：is_self 为真，或 sender 等于 self_id 时，消息事件直接丢弃。
•  顶层字段：所有上报的业务事件都带 time、self_id、post_type，以及 ling（原始微灵事件，见 5.8 节）。
•  时间：微灵 send_time 为毫秒（大于 1e11）时自动除以 1000；缺失或为 0 时取当前时间。
•  昵称：取微灵事件的 sender_name；sender.card 与 nickname 相同，sender.role 固定为 member（微灵事件不提供群角色）。
5.2　消息事件总览
下表为消息类事件的一览，详细字段见 5.3 节：
表 5-1　消息事件映射

媒体可用性　图片、视频、文件只有在微灵事件自带 CDN 直链（cdn.url）时才能被对端下载；同时微灵会把该直链登记到媒体缓存，get_image/get_record/get_file 可凭消息段中的 file 值按需取回（见 7.6 节与第 8 章）。位置、链接、名片分别映射为 location / share / contact 段，详见 5.3.3 节与第 6 章。
未映射消息（11200）　11200 是微灵 5.0.13.6005 的「未映射消息」兜底类型：能识别出正文与 at_list 的按普通消息透传；read_receipt/已读上报等非聊天内容会被过滤并记日志，避免污染 OneBot 消息流。
5.3　消息段字段详解
5.3.1　文本与 @（11041）
文本消息在群聊中若带 at_list，先生成 at 段，再生成 text 段；私聊只生成 text 段。at 段的 qq 为数字字符串。at_list 中只有 user_id 可解析为数字时才生成 at 段；@自己也会保留。rich_text 不逐段解析：只取 content/text 与 at_list（见第 6 章）。
代码 5-1　文本 + @ 的消息段
{
  "message": [
    { "type": "at", "data": { "qq": "168800001" } },
    { "type": "text", "data": { "text": " 请查收" } }
  ],
  "raw_message": "@168800001 请查收"
}
•  群消息带 at_list 时，at 段在前；文本内容取 content（缺失时取 text）。
•  raw_message 中 @ 的形式为 @<数字QQ>，不是昵称；需要昵称请读取 at 段或 sender。
•  text 段内容为空时仍会生成（消息只含 @ 的场景），由对端自行处理。
5.3.2　图片、动图、视频、语音、文件
表 5-2　媒体消息段字段

•  无 URL 时不会生成媒体段：图片降级为文本 [图片]，视频为 [视频]，动图为 [动图]。
•  record 段只有 file（微灵 CDN c2c_cdn.file_id），事件不带下载 URL；get_record 只有在对端直接传入 http(s) 直链时才可能成功，直接传 file_id 会返回失败（见 7.6 节）。
5.3.3　结构化消息段（位置、链接、名片）
•  位置（11046）→ location 段：lat 取 latitude/lat，lon 取 longitude/lon/lng，title 取 title，content 取 address。
•  链接（11047）→ share 段：url 取 url，title 取 title，content 取 desc，image 取 image_url（可选）；url 与 title 都为空时降级为文本。
•  名片（11050）→ contact 段：type 固定为 qq，id 为数字 user_id；user_id 不是数字时降级为文本 [名片] <昵称>。
•  以上字段缺失时会给出空字符串；对端应做容错，不要把空串当作有效值。
5.3.4　消息公共字段

无需 client/getData 参数　动作请求不需要传 client 参数，也不需要传 getData。微灵使用事件中记录的 client token（默认 1）与微灵通信；查询类指令（11038/11036/11040/11039）由 shim 自动附加 getData:true。对端只需按标准 OneBot v11 传业务参数。
7.2　发送消息
7.2.1　参数与消息解析
•  send_group_msg 必填 group_id；send_private_msg 必填 user_id；二者均必填 message。
•  message 支持字符串（按纯文本处理）与消息段数组。
•  识别的段类型：text、at、image、video、file、GIF（image 且 type/sub_type 含 gif，或文件扩展名为 .gif）。
•  text 拼接为正文；at 收集 qq 值（数字 ID 会以数字形式写入 at_list）；at 的 qq 为 all 时无法 @ 全体，退化为纯文本；reply 与 face 段被静默忽略。
•  record 段不支持（微灵没有语音发送指令）；json/xml/forward/node 等其余类型返回失败。
•  正文为空且没有任何可发送段时返回失败 empty message；只有 @（无文本）也是合法消息。
•  群消息带至少一个 at 时走指令 11069；否则走 11029。
•  私聊会话 ID 为 S:<user_id>_<self_id>，群会话 ID 为 R:<group_id>。
•  含媒体的消息会拆成多条微灵命令：媒体先发（图片 11030、视频 11067、文件 11031、动图 11070），文本/@ 后发；媒体文件落在微灵程序目录的 onebot_media_tmp 临时目录，详见 8.2 节。
•  onebot_media_tmp 会随发送量增长并占用磁盘（单文件最大约 32MB，后台清理 1 小时前的文件）；高频发送媒体时请关注该目录体积。
7.2.2　请求与响应示例
代码 7-1　发送群消息（带 @ 与图片）

      { "type": "image", "data": { "file": "C:\\media\\ok.png" } }

7.5　消息查询与能力
•  get_msg：按 message_id 查询本进程缓存的消息事件（最多 500 条，先进先出）；命中返回完整的 message 事件 JSON（含 ling），未命中返回失败 message not found: <id>。
•  get_group_msg_history：接口兼容存在，但微灵不提供历史消息，固定返回空数组 []。缓存只包含改造版上报过的消息，重启微灵后清空。
•  can_send_image / can_send_record 固定返回 { "yes": true }，表示协议层面的能力查询结果；实际出站图片/视频/文件/动图已支持（见 8.2 节），语音（record）仍不支持。
7.6　媒体与文件动作
说明　微灵会把入站消息自带的 CDN 直链登记到媒体缓存；下列动作在命中缓存（或调用方直接传入 http(s) URL）时按需下载并返回 base64://，或直接返回 CDN 原始地址。无直链、下载失败或超出限制时返回失败。出站媒体发送见 8.2 节。
表 7-5　媒体动作与行为

•  get_image/get_record/get_file 优先读参数 file，缺失时读 file_id；命中缓存后按需 HTTP 下载（15s 超时，单文件最多约 32MB，超出会截断），返回 base64:// 内容与 file_name。
•  缓存键来自入站消息段：图片为 cdn.md5/cdn.file_name，动图为 name，视频为 cdn.file_name/cdn.md5，文件为 server_id/local_id；对端应原样使用事件消息段里的 file 值。
•  get_group_file_url/get_private_file_url 优先读 file_id，缺失时读 file；命中时直接返回微灵 CDN 原始 URL（见 8.3 节），不依赖本地媒体服务。
•  get_record 最特殊：11044 语音事件只带 file_id、不带 CDN 地址，因此只有调用方把 file 传成 http(s) 直链时才可能成功。
•  本地媒体服务（127.0.0.1:18890–18920）仅在缓存到字节时兜底启动；当前版本没有写入字节缓存的调用路径，正常路径不会启动。

表 7-6　不支持动作的两种返回

8　媒体与文件
本章说明消息中的媒体与文件如何表示、如何取回，以及出站媒体如何发送。总览：入站媒体依赖事件自带的 CDN 直链；出站媒体已支持图片、视频、文件、动图，语音（record）仅有入站能力。
8.1　入站媒体
微灵的事件会在消息段中携带 CDN 信息。改造版按以下规则生成 OneBot 消息段，并同时把可用的 CDN 直链登记到媒体缓存，供后续动作查询。
表 8-1　入站媒体映射

•  有直链的媒体会登记到媒体缓存；get_image/get_record/get_file 可凭消息段里的 file 值取回（按需下载后返回 base64://），get_*_file_url 可拿到原始 CDN 地址（见 7.6 节）。
•  无 cdn.url（且没有回退地址）时无法取回，消息段会降级为文本 [图片]/[视频]/[动图]。
•  record 只有 file_id，没有直链；get_record 只有在调用方传入 http(s) URL 时才可能成功。
•  位置、链接、名片分别映射为 location、share、contact 段，不涉及媒体缓存，详见 5.3.3 节与第 6 章。
CDN 时效　CDN 地址通常有时效。收到消息后应尽快处理媒体；需要长期保存的内容请在业务流程里自行转存，不要依赖事件里的 url 永久有效。
8.2　出站媒体
出站媒体已支持。OneBot 消息中的媒体段由 shim 统一落地为本地临时文件，再以微灵发送指令发出；一条含媒体与文本的消息会被拆成多条微灵命令（媒体在前、文本在后）。
8.2.1　支持的媒体与微灵指令
表 8-2　出站媒体与微灵指令

8.2.2　媒体来源与临时文件
•  file 字段支持：base64:// 内联数据、http(s) URL、file:// URI、本地绝对路径。
•  http(s) 源由 shim 下载（15s 超时），单文件超过约 32MB 或下载失败直接返回失败。
•  base64:// 内容解码失败、本地路径不是绝对路径、文件不存在，都会返回明确错误（见表 7-2）。
•  下载/解码后的内容写入微灵程序目录的 onebot_media_tmp 临时目录，文件名形如 media_<时间戳>_<自增ID>.<扩展名>；扩展名优先按文件头判断（png/jpg/gif/webp/mp4），否则取源文件名扩展。
•  后台会清理该目录中 1 小时前的旧文件；磁盘紧张时可手工清空，不影响运行中的发送。
•  临时文件随发送量增长而占用磁盘（单文件最大约 32MB）：高频发图/发文件的实例应定期检查 onebot_media_tmp 体积，避免系统盘被占满。
•  媒体命令执行失败时整条动作返回失败（发送媒体失败(<类型>): ...），已发出的媒体不会撤回。
代码 8-1　发送带图片的群消息
{
  "action": "send_group_msg",
  "params": {
    "group_id": 24680001,
    "message": [
      { "type": "image", "data": { "file": "base64://iVBORw0KGgo..." } },
      { "type": "text", "data": { "text": " 请看这张图" } }
    ]
  }
}

// shim 侧大致行为
// 1. 解码 base64 -> onebot_media_tmp\media_20261113...png
// 2. 调用微灵 11030 {conversation_id: "R:24680001", file: "<程序目录>\onebot_media_tmp\media_...png"}
// 3. 调用微灵 11029 {conversation_id: "R:24680001", content: " 请看这张图"}
8.2.3　已知约束
•  每条媒体都会先落盘，微灵进程需要对程序目录有写权限；建议使用可信目录运行（见 3.1 节）。
•  媒体与文本是两条微灵命令，群成员会看到媒体消息与文本消息各一条。
•  微灵侧命令执行失败不会自动重试；对端可根据 retcode/msg 决定是否重发。

9　个人微信通道（实验性）
实验性能力　个人微信通道的 OneBot v11 支持是实验性的：事件映射依赖启发式字段，能力远少于企业微信通道，且默认不启用。生产环境请优先使用企业微信通道。
改造版为个人微信通道提供了独立的 OneBot v11 连接（与企微通道分开配置、分开连接）。本章说明其启用方式、事件映射与能力边界。
9.1　启用方式
步骤 1　在微灵界面切换到「个人微信」通道，完成个人微信登录。
步骤 2　通信方式选择 WebSocket，并在该通道的地址栏填写 OneBot 实现的反向 WS 地址。
步骤 3　填写 Token（与 OneBot 实现一致；可为空）。
步骤 4　保存并启用。与企微通道不同，个微通道没有默认地址：地址为空时不会发起连接。
步骤 5　在 OneBot 实现侧确认连接到来，并检查 self_id 是否正确（个微通道依赖事件携带 robot_id 或登录信息）。
•  个微通道与企微通道可以同时连接同一个 OneBot 实现，但建议使用不同适配器或通过 X-Self-ID 区分。
•  个微通道不做 HTTP self_id 探测，因此不会访问 8060 端口；self_id 完全依赖事件。
9.2　事件映射
个微通道的事件结构与企业微信不同，改造版采用启发式字段匹配：先看常见字段名，取到即用。事件类型不是整数（或缺少可识别字段）时按消息处理。
表 9-1　个微事件字段映射（启发式）

•  消息事件固定为 message，message 只含一个 text 段；sub_type 恒为 friend。
•  room_id 非空时 message_type 为 group 并带 group_id；否则为 private 并带 user_id。
•  事件同样附带 ling，保留个微原始事件，便于对端自行解析媒体等缺失信息。
•  由于字段是启发式的，不同微灵小版本或不同消息类型可能无法映射；此时事件被忽略。

10　保留能力与兼容性
改造只替换了 WebSocket 通信层：微灵原有的 HTTP API、HTTP 事件回调、配置体系全部保留。本章说明哪些能力不受影响、如何与 OneBot 通道共存，以及升级/回滚方式。
10.1　微灵原有 HTTP API 保留
•  企业微信 HTTP 接口（POST /api/Client/ExecCommand 等）行为不变，仍可按官方文档调用。
•  个人微信 HTTP 接口（POST /api/PersonalWeChat/ExecCommand、/api/PersonalWeChat/Clients 等）行为不变。
•  HTTP API 与 OneBot 通道可以同时使用：例如运维脚本通过 HTTP 发消息，机器人通过 OneBot 收发。
•  shim 自身的 self_id 探测也走 HTTP（127.0.0.1:8060 的 11035 指令），因此修改 HTTP 端口会影响连接（见 12.1 节）。
10.2　HTTP 事件回调
微灵原有的“事件通知 URL”（config.ini 中的 CallbackUrl）配置仍然有效。改造版在事件入口处先尝试投递 OneBot 连接，返回结果告知宿主是否已投递；宿主可据此决定是否继续走原有 HTTP 回调。
表 10-1　事件通道选择

避免双投递　改造版不会把“OneBot 投递失败”自动转为 HTTP 回调重发：是否回落由微灵宿主逻辑决定，且未连接期间的事件不会被缓存补发。需要可靠双通道时请自行做幂等与去重。
10.3　配置与界面
•  不新增配置文件；OneBot 地址与 Token 在微灵界面填写，仍由微灵写入 config.ini。
•  登录、二维码、账号面板、日志、更新等原有界面与流程不变。
•  程序目录新增 onebot_v11.log（协议日志），不影响原日志文件。
•  部署组件与未改造版本一致，仅多一个 OneBotShim.dll；无需安装额外运行时（依赖 .NET Framework 与原程序一致）。
10.4　通道互斥与保持在线
微灵 1.11.0 的通信通道存在互斥特性：同一通道同一时间只使用一种通信方式，且 WebSocket 尚未连接成功时，事件可能不会投递。因此：
•  启动顺序：先启动 OneBot 实现，再启动/登录微灵（见 2.4 节）。
•  保持微灵账号在线：退出登录会清空 self_id，连接停止，事件不再产生。
•  避免频繁切换通信方式：切换会重建连接，切换期间的事件可能丢失。
•  网络抖动导致重连时，重连窗口内的事件不补发；需要强可靠性的场景应在微灵侧或对端做补偿。
•  同一账号不要同时连接多个 OneBot 实现（同一微灵实例只维护一条连接）；多实现需求请拆分为多个微灵实例。
10.5　升级与回滚
表 10-2　升级与回滚

•  升级前建议导出一份 config.ini 与微灵账号配置，便于快速恢复。
•  回滚后 onebot_v11.log 不再增长，可保留作为历史记录。
10.6　安全注意事项
•  Token 以请求头传递，不出现在 URL；但仍应使用强口令，避免被内网嗅探。
•  跨公网务必使用 wss://，并在反向代理/防火墙层限制来源。
•  onebot_v11.log 包含事件内容（含 ling 原始事件），可能含昵称、群名、消息文本；请按敏感日志管理并定期清理。
•  对端实现应校验 Authorization，不要以“内网”为由留空 Token。

11　AI 审批插件
本章介绍与改造版配套使用的第三方 AstrBot 插件 astrbot_plugin_ai_approval（AI 审批）。它是运行在 AstrBot 侧的独立插件，不是桥接层（OneBotShim）的功能：桥接层只负责企业微信消息与 OneBot v11 之间的转发，审批规则、解析与审计都由插件完成。
11.1　功能概览
•  实现状态与源码位置：插件源码已生成于 D:\wecom-ling\onebot\plugin_ai_approval\（main.py、README.md、metadata.yaml、_conf_schema.json），为 AstrBot v4 插件（Star 基类），聊天消息驱动，不依赖桥接层；安装到 AstrBot 实例后即可使用（见 11.4 节）。
•  员工在审批群或私聊中按自然语言或约定结构提交审批内容（申请人、类型、事由、天数、金额、时间）。
•  插件解析提交内容，并按配置的规则判定是否满足自动通过条件；满足则回复通过回执。
•  不满足规则时，插件把审批内容转发到管理员群提醒人工处理。
•  所有提交、判定与结果写入 JSONL 审计日志，便于追溯。
•  提供管理员命令：/ai审批帮助、/ai审批规则、/ai审批记录。
不是原生审批　这是聊天消息驱动的审批流程，不是企业微信原生审批。企业微信原生审批的“同意/拒绝”没有开放接口，微灵 Hook 也不提供该能力，插件只能基于群/私聊消息与规则近似实现。
11.2　工作流程
步骤 1　员工提交：在审批群或私聊中发送审批内容。支持自然语言（如“我明天请一天年假，事由……”）和结构化写法（申请人/类型/事由/天数/金额/时间）。
步骤 2　解析：插件提取字段；开启 use_llm 时调用 AstrBot 侧配置的 LLM 供应商解析自然语言。
步骤 3　规则判定：按 auto_approve_types、auto_approve_max_leave_days、auto_approve_max_amount 等配置判断是否自动通过。
步骤 4　结果处理：满足条件时回复通过回执；不满足时转发到 admin_group_ids 指定的管理员群并 @ 管理员。
步骤 5　审计：把原始提交、解析结果与判定写入 audit_log_path 指向的 JSONL 文件。

11.5　边界与说明
•  插件是第三方组件：升级 AstrBot 或插件版本前先确认兼容性，停用插件不影响桥接层与 OneBot 连接。
•  自动通过只依据配置规则与解析结果，不替代企业微信原生审批；重要审批建议关闭自动通过，统一转管理员群人工处理。
•  LLM 解析存在不确定性：建议要求员工按结构化格式提交，或在提示词中约束字段。
•  审计日志是本地 JSONL 文件，请纳入备份与权限管理；日志内容含申请人、事由等敏感信息。
•  插件默认不启用（未配置 approval_group_ids 时不响应任何群消息）。
•  若 AstrBot 的插件规范或安装目录随版本变化，以实际安装目录与版本为准；插件本身是 AstrBot v4 插件（Star 基类），不修改微灵与桥接层。

12　已知限制与排障
本章先给出改造版的完整限制清单，再给出常见问题的排查路径与日志关键字。建议对接前先浏览限制清单，避免把“实现边界”误判为“配置错误”。
12.1　self_id 与连接相关限制
•  未登录不连接：微灵需要先取得 self_id 才会发起连接；账号离线时只重试不连接。
•  self_id 探测硬编码：企微通道通过 http://127.0.0.1:8060/api/Client/ExecCommand（指令 11035）探测账号，端口与地址不可配置。若把微灵 HTTP 端口改为非 8060，探测会失败，只能依赖登录事件（11026/11179）提供 self_id。
•  探测每 15s 一次：首次连接前最多等待约 15s 才能拿到 self_id，属正常现象。
•  个微通道无探测：只依赖事件中的 robot_id/账号字段，取不到就不连接。
•  地址非法不连接：地址无法解析为绝对 URI 时只记日志并重试，不会尝试兜底地址。
•  无固定静默断连：接收循环按秒轮询 socket 状态；发送线程的 120s 入站静默看门狗已移除，对端长时间不发帧不会导致断连，连接有效性由 WebSocket/TCP KeepAlive 与发送失败发现（见 4.6 节）。

12.3　动作与发送相关限制
•  出站媒体支持但有约束：支持 text/at/image/video/file/gif（图片 11030、视频 11067、文件 11031、动图 11070）；record 不支持（微灵无语音发送指令）。详见 8.2 节。
•  reply 与 face 段被忽略：AstrBot 默认回复带的 reply 段不会导致失败，正文照常发送；face 段忽略。
•  @全体降级为纯文本：at 的 qq 为 all 时不写入 at_list，群消息退化为普通文本（11029）。
•  媒体与文本分多条发送：一条含媒体的 OneBot 消息会先按媒体依次调用 11030/11031/11067/11070，再发送文本段（11069/11029），对端会看到多条微灵侧记录。
•  rich_text 不逐段解析：文本事件只取 content/text 与 at_list，图文混排请读取 ling。
•  get_group_msg_history 返回空数组：微灵不提供历史消息查询，只能查本进程 500 条缓存。
•  媒体动作依赖直链：get_image/get_record/get_file 需命中媒体缓存（或传入 http(s) URL）才能按需下载并返回 base64://；无直链、下载失败或超限时返回 500（见 7.6、8.4 节）。
•  动作串行执行：接收循环中同步执行动作，单个动作最长可阻塞 60s；期间事件积压、心跳由独立发送线程维持。
•  发送队列上限 2000：溢出时丢弃最旧帧并记日志；高频发送时可能丢失动作响应或事件。
•  单帧发送超时 10s：网络差时可能触发断连重连。
•  临时媒体目录占用磁盘：出站媒体先落到程序目录 onebot_media_tmp（单文件最大约 32MB，后台清理 1 小时前文件）；高频发送图片/文件时该目录会累积，注意磁盘余量。
•  显式不支持的动作返回 500：set_group_name、set_group_card、set_group_ban、set_friend_add_request、set_group_add_request；未知动作返回 1404。
•  不支持自动通过好友/入群申请：11063 只上报，不能自动处理。
•  发送失败原文：微灵未返回结果（超时或未登录），多与微灵登录状态或指令通道有关。
12.4　媒体相关限制
入站媒体可经事件自带的 cdn.url 直链取回：命中媒体缓存后，get_image/get_record/get_file 按需下载并返回 base64://；get_*_file_url 直接返回 CDN 原始 URL。无直链的媒体无法取回，语音事件只有 file_id；出站媒体支持图片/视频/文件/动图（语音除外），但需要可访问的本地文件或可下载的 URL，临时文件写入程序目录 onebot_media_tmp（单文件最大约 32MB，随发送量占用磁盘，1 小时后自动清理）；本地媒体服务仅在缓存到字节时兜底、正常不会启动。详见 8.4 节，此处不重复。
